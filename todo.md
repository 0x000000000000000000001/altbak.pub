# Optimization techniques by backend

Audit dated **September 9, 2026**: **53 techniques across 11 backends**, cross-checked against their invoked passes and code generation paths. This matrix describes integration, coverage, and limitations. It serves as a work list; **it is not a ranking of backend speed**. The reference measurements remain those in the [README](README.md).

All eleven backends referenced by the runners are included. **Our five backends occupy the first columns: sharpurs, purust, phpurs, gopurs, and javapurs.** The other six follow on the right: psgo, official JS, ES, purescm, purerl, and Wasm, which is experimental across the 14 core cases. The README's “Native FP-style” and “Native hand-optimized” columns are handwritten implementations: their shortcuts are not attributed to the compilers.

## Rating legend

- 🟢 **Complete within the defined scope**: the mechanism is integrated and used by the relevant code generation path. This does not certify every possible program.
- 🟡 **Partial**: a significant restriction on types, expression shapes, local/intermodule scope, ABI, or code generation path. [Audit notes](optimization-audit.md#exact-scope-of-the-rows) explain the restriction.
- 🔴 **Missing**: no corresponding mechanism is integrated into the audited pipeline; a primitive, prototype, or unused module is insufficient.
- ⚪ **Gray — unnecessary / not applicable in this form**: the target's representation, value management, or native tail calls already cover the need. Gray cases are explained in the [audit notes](optimization-audit.md#exact-scope-of-the-rows).

**🟢 (PBO) / 🟡 (PBO)**: the shared PBO infrastructure provides a transformation or analysis actually used for this capability, sometimes complemented by the target code generator. The label means neither that PBO implements the entire technique on its own nor that all backends use it with the same coverage. It distinguishes this contribution from passes belonging to the backend, the PureScript frontend, or the runtime. For ES and purescm, it refers to their version of PBO, not our fork's TAST extensions.

A conservative proof of purity, arity, or non-escape is necessary for correctness; it is not inherently a shortcoming. “Partial” identifies a coverage limit worth knowing about. These cells should not be added up into a maturity percentage: some rows depend on the same passes and carry different weight.

**Row order defines performance-investigation priority, highest first**, across our five backends and the core benchmarks. Skip capabilities already complete for the backend being improved. The first ten rows cover broad transformations and their representation prerequisites; rows **11–12** add the foreign-call bridge and the string payload representation; rows **13–17** group ADT layouts, FBIP, field-level reuse specialization, borrowing and Perceus-style reference-count optimization. Sticky sharing is last because no current hot-path benefit has been established. This is a qualitative order; each proposed gain still needs an isolated measurement. ## Latest Gopurs integrations

- **No displayed cell changes (22–27 September); D3/D4/D6/D23/D28/D40 remain yellow.** The backend now runs ordinary beta reduction after PBO ([ImmediateApplications](../gopurs/gopurs/src/Gopurs/ImmediateApplications.purs)), hoists closed class-typed dictionary constructions into top-level `sync.Once` getters ([ClosedDictionaries](../gopurs/gopurs/src/Gopurs/ClosedDictionaries.purs) — a global cache, deliberately not row 19), shares one native worker across proven record shapes with foreign forwarders excluded from specialisation, keeps `[]int64` for recognised `Data.Array` map/foldl/filter/index paths, lowers qualified Array/Object/Either traversals with native callbacks and one fresh output map, specialises Argonaut decoder shapes only through their standard qualified dictionaries, and lowers known pure foreign calls through typed workers instead of the `_Gopurs_*` wrapper. The [fused traversal campaign](docs/benchmark-results/2026-09-22-fused-json-traversals.md) gives JSON Decoding **31.79 → 24.94 ms** and JSON-to-typed-AST **531.30 → 498.37 ms** combined (17 JSON and 12 TAST oracles; 171 compiler tests); the [record-worker probes](docs/benchmark-results/2026-09-22-native-record-workers.md) give 18–41× on isolated reader pipelines with 0 allocations. The rejected field-update and static-cell prototypes remain unintegrated.
- **D3/D4 remain yellow; D49: red → yellow (17 September).** A typed recursive function producer `build 0 = identity; build n = let previous = build (n - 1) in \f x -> f (previous f x)` now captures its nonnegative count and calls a loop worker. Saved functions, partial applications, callback order and the original negative body are preserved. The rule is structural, limited to `Int -> (Int -> Int) -> Int -> Int`; callbacks still use the existing `Value` ABI. Five alternating probe pairs from the actual generator give **Church 490.800 → 236.358 µs**, all favorable, with **157 → 112 allocations** and **6,800 → 5,280 bytes** per calculation. The full runner confirms **486.04 → 233.92 µs**, then **480.54 → 236.29 µs** in a second series. **A stable total-suite improvement is not established**: other rows fluctuate enough to mask the Church saving. Build and bundle have no warnings; **97 tool tests**, the new TAST fixture and the existing ThunkFusion fixture pass. [Scope, full results and unchanged README baseline](scratch/gopurs-counted-functions-20260917/REPORT.md).

## Latest Purust integrations

- **B6: red → yellow (PBO) (26 September).** The backend ports the Go global specialiser: [Monomorphization](../purust/purust/src/Purust/Monomorphization.purs) matches the production Gopurs pass, runs before `buildModules` when `--monomorphize` is passed, keeps `negate` and value-level foreign forwarders generic, and specialises only at call sites inside the defining module. The audited `bin/rust` runner does not pass the flag, and no test or paired measurement is recorded, so the cell stays yellow; this replaces the earlier statement that no pass creates clones per instantiation.
- **B28 and B40: red → yellow (26–27 September).** `Array Int` values keep their elements unboxed: `Data.Array.range` and `Int` `replicate` create `Value::IntArray` (`Rc<Vec<i64>>`), `reverse`, `filter` and `slice` keep that representation, indexed reads use `array_get_int`, and a self-recursive loop that captures such an array is emitted twice, the selected variant reading a borrowed `&[i64]` slice. Recognized `Data.Foldable.foldlArray`/`foldrArray`, `Data.Array.filterImpl`/`anyImpl`/`allImpl`/`unsafeIndexImpl` and length/count patterns emit `purust_core::typed::*` loops with native element and accumulator types instead of materializing intermediates, and [ListFusion](../purust/purust/src/Purust/ListFusion.purs) fuses `foldl` over `filter` over `range` (commutative Int operations) and `filter` plus `reverse` into one loop, covered by the [fresh-TAST fixture](../purust/purust/tests/tast/list-pipeline.mjs). The generated `Test.ArrayOps` kernel calls `typed::filter` and `typed::sum_filter_range`, and `Test.ListOps.sumEvens` is one countdown loop with no list nodes. Boxed elements, literals, opaque producers and non-commutative folds keep their previous paths; the [array-indexing diagnostic](../purust/purust/docs/array-indexing-benchmark.md) records the representation and access rules.
- **B15 remains yellow: proven three-cell reconstructions now permute fields in place.** The first guarded branch may reconstruct an LL- or RR-shaped chain of three identical constructors, with two recursive fields at arbitrary positions and all remaining fields native Copy. A TAST proof preserves every frontier subtree exactly once; the root cell remains the root. All tag/uniqueness checks and scalar snapshots precede writes. Other branches, unsupported layouts, computed scalars, conversions and shared/weak cells retain the existing path. Five alternating pairs of full runners give **RBTree 12.469 → 11.928 ms (−4.34%)** and **sum of benchmark medians 13.427 → 12.888 ms (−4.01%)**, with all five pairs favorable. **77/77 codegen tests** pass after an environmental retry; **33/39 TAST tests** pass, with the six existing failures reproduced without the new rule and the new fixture passing. These paired measurements are separate from the historical README and the earlier prototype. [Scope, validation and measurements](scratch/rust-field-permutation-integration-20260914/REPORT.md).

- **B16 remains yellow; B25 remains green: scalar record projections now borrow their path.** A local root and closed TAST rows prove each field down to an `Int`, `Number`, `Boolean` or `Char`, copied immediately. Owned results, open rows, opaque receivers and incompatible conversions keep their existing paths. ## Latest Sharpurs integrations

- **A14/A15: red → gray; no other cell changes (24–25 September).** The ownership/mutation lever was measured and refuted for this column: a Release prototype of the same Okasaki algorithm compared persistent unions against mutable nodes in two field styles and found mutation **~45 % slower** (51.7–52.0 vs 35.65–36.36 ms per 100 000 insertions), because .NET nursery allocation is a bump pointer while mutating promoted nodes pays write barriers. No compiler change was kept; the cells are gray *not applicable in this form*. Separately, the shared PBO now aligns class-member annotations with scoped type variables (`alignClassMemberAnnotations`), so `IntKernel` accepts the Polymorphism loop: **Polymorphism 287.91 → 2.52 ms**, **total 339.60 → 58.63 ms** on three validated official processes. ## Latest Phpurs integrations

- **C14/C15/C46: red → yellow (24–25 September).** [ArrayRefs](../phpurs/phpurs/src/Phpurs/ArrayRefs.purs) promotes a private worker parameter to a PHP reference only when a fixpoint proof shows every call site hands over ownership (last use of an owned parameter, a field of an owned parameter, or a consumed TCO loop register whose carrier is released). A rebuild of the owned node then writes only the changed fields and returns the node; a rebuild whose fields are all unchanged returns the node without allocation or write. Literals, live bindings and call results keep the by-value parameter, so shared values are never mutated; rotations and leaves still allocate. Native runner: **RBTree ~104 → 59.79 ms**, **suite 116.59 → 72.94 ms**, codegen **10/10**, no JIT corruption. The same series made `EnumRegions` select a region from the head worker's signature instead of a `Typed` annotation (compiled column **262.81 → 121.52 ms**), removed the private constructors' unused `$tag` (≈120.1 → 115.2–116.6 ms), and translated Ref/ST primitives to `phpurs_ref_*` helpers (support only; row 38 stays red). The private array representation remains withdrawn.

## Latest Javapurs integrations

- **E46: red → yellow; no other cell changes (24–25 September).** [Reuse](../javapurs/javapurs/src/Javapurs/Reuse.purs) shares a constructor rebuild with its source: a rebuild whose every argument is the source's own projection returns the source, and a rebuild with exactly one object field replaced by a shared nullary constructor emits a runtime equality test that returns the source when the field already matches (primitive fields are excluded because reference equality is not value equality). [Reuse guards](../javapurs/javapurs/test/constructor-reuse.mjs) compile and run both shapes. `Ownership` also consumes local recursive groups, polymorphic tree families and freshly built trees in place (rows 14/15 keep their yellow scope), recursive definitions without a back edge keep primitive parameters without loop storage (RBTree 16.60 → 16.05 ms, Fib 0.193 → 0.115 µs over isolated pairs), and Ref/ST primitives now translate to one-element `Object[]` references (support only; row 38 stays red).

## Perceus, FBIP and sticky sharing

These names describe related but distinct mechanisms. **Perceus** combines precise reference counting, reuse analysis and specialization; **FBIP** means *functional but in-place*, where functional code can reuse uniquely owned storage while preserving shared values. A runtime pointer named `PerceusPtr` alone does not establish the complete compiler algorithm. See the [Perceus paper, sections 2.2–2.7](https://www.microsoft.com/en-us/research/wp-content/uploads/2020/11/perceus-tr-v4.pdf).

| Mechanism | Priority / matrix cells | Current Purust scope |
| --- | --- | --- |
| **FBIP / reuse analysis** | **14 — B14**, with fixed-field record updates in **B25** | Partial for ADTs: recognized consumed nodes and rotations reuse unique `Rc` cells, with a copying fallback when required. Record setters use `PerceusPtr::make_mut`. Neither cell claims universal in-place execution. |
| **Reuse specialization: leave unchanged ADT fields in place** | **15 — B15, partial** | [ReuseFields](../purust/purust/src/Purust/ReuseFields.purs) updates one scalar field of a uniquely owned ADT, preserving unchanged fields in place; shared/weak cases retain the reconstruction fallback. [ChildCalls](../purust/purust/src/Purust/ChildCalls.purs) and [ChildUpdates](../purust/purust/src/Purust/ChildUpdates.purs) extend this to one child consumed by a closed native call, with a proven constructor-only helper branch and scalar/recursive layout. [ChildBranches](../purust/purust/src/Purust/ChildBranches.purs) also proves guards on the returned child, preserving ordered tag tests and dominated projections; complex branches consume that computed child exactly once. [FieldPermutations](../purust/purust/src/Purust/FieldPermutations.purs) and [FieldPermutationPrinter](../purust/purust/src/Purust/FieldPermutationPrinter.purs) additionally preserve fields during a proven first-branch three-cell permutation. Other reconstruction shapes, opaque calls, conversions and shared/weak cells retain their existing paths. Fixed-field record setters belong to **B25**. **B46** is different: returning the original constructor when the replacement is already equal. |
| **Last-use moves / borrowing; propagation of uniqueness** | **16 — B16, partial**, also **B14** | Selected moves and borrows are integrated, including closed-record roots moved after replacement values at last use and a closed record path detached after all RHS values. Existing setters reuse unique roots/children/leaves with copying for shared versions; only the three initial cells allocate in Records. The rule follows one child per level, not every sibling branch. Closed record projections from locals can also borrow the entire path and immediately copy an Int/Number/Boolean/Char; escaping values and unproven paths keep owned getters. The new closed child-call path retains its mutable borrow across recursion and avoids its reconstruction retest; other ADT paths can still retest uniqueness, and read-only traversals can clone child pointers. |
| **Perceus: release specialization and dup/drop fusion** | **17 — B17, missing** | No branch-local compiler pass over reference-count operations was established. Existing last-use moves, borrows and ownership transfers retain their credit in **B14/B16**; they do not by themselves establish this additional transformation. |
| **Sticky sharing / saturating reference counts** | **53 — B53, partial** | `PerceusPtr` saturates at `u32::MAX`; subsequent clones/drops leave the count unchanged and the object stays alive. Native ADTs such as RBTree use `std::rc::Rc`, so this mechanism does not apply to that path. No benchmark gain is attributed to saturation. |

Evidence: [ownership and reuse](optimization-audit.md#purust), [record setters and last-use generation](../purust/purust/src/Purust/CodeGen.purs), and the [saturating pointer runtime](../purust/purust/tests/runtime/perceus_ptr/src/lib.rs). The [Purust plan](../purust/purust/todo.md) breaks the remaining work into measured baby steps. Shared nullary constructors in **B45** are another distinct mechanism: sharing a value does not imply an immortal or saturated reference count.

The three added mechanisms have separate stable audit IDs **47–49**. Existing ratings are retained with their techniques; displayed coordinates change with the priority order. The audit explains the scopes and the gray cells for targets without backend-controlled reference counting.
