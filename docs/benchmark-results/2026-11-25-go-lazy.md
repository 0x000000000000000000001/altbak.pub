# Lazy : optimisation Go — 25 novembre 2026

Lazy passe de **746,503 ns à 12,948 ns**, soit une accélération de **57,65×**
dans une campagne avant/après alternée. Son ratio Go/C passe de **665,72× à
11,55×**. Les benchmarks, leur harnais, le FFI et la référence C impérative
sont inchangés. L’entrée reste opaque à chaque invocation.

Les [données et preuves](2026-11-25-go-lazy.json) conservent les échantillons,
sorties brutes, manifestes, changements du compilateur, tests, extraits Go et
contrôles d’opacité.

## Les quatre indicateurs Go/C

Les mêmes quatorze médianes C impératives servent de dénominateurs aux deux
versions Go. Elles viennent de la campagne avec entrées opaques.
Ni le C ni JavaScript ne sont remesurés ici.

- Ratio des totaux : **1,141867× → 1,146216×**.
- Moyenne arithmétique μ : **54,908534× → 8,124051×**.
- Médiane Q₂ : **7,231110× → 7,173423×**.
- Moyenne géométrique G : **4,103827× → 3,070195×**.

Le total Go est de **10,001490 ms avant** et **10,039576 ms après**, pour
**8,758890 ms en C**. Les calculs utilisent les temps avant arrondi : ΣGo/ΣC
pour le ratio total, puis la moyenne, la médiane et la moyenne géométrique des
quatorze ratios. Les 23 cas Incl WIP ne participent pas à ces indicateurs.

La [publication précédente](2026-11-25-go-church-state.md) donnait respectivement
**1,154000×**, **55,639467×**, **7,320738×** et **4,127068×**, avec Lazy à
**758,293 ns**. Les gains annoncés ici utilisent la nouvelle paire avant/après,
qui réexécute aussi les anciens binaires.

Le gain propre à Lazy économise **0,734 µs** sur un total proche de **10 ms**.
Il réduit donc surtout μ et G. La variation du total (+0,38 %) ne démontre
aucun changement de performance globale : les plages des totaux par processus
se recouvrent, **9,875–10,012 ms avant** et **9,871–10,353 ms après**. Le code
des autres cas est identique ; leur variation de mesure contribue aux écarts
du total et de la médiane. L’objectif de 1× sur les quatre indicateurs n’est
pas encore atteint.

## Transformation du compilateur

Le Go précédent avait déjà supprimé les thunks, mais la boucle externe
conservait 1 000 appels au même calcul entier fermé. `ClosedScalar` reconnaît
désormais une récurrence prouvée à deux paramètres Int : compteur décrémenté
de un, retour de l’accumulateur à zéro, ajout d’une constante et auto-appel
exact sans travail supplémentaire.

Le résultat fermé est calculé avec la même arithmétique modulo 2³² que les
additions répétées. Le produit est décomposé en morceaux de 16 bits pour rester
exact sur les hôtes JS et natif. Le cas zéro rend l’accumulateur intact.
L’évaluation stricte du callee et des arguments précède le raccourci ; le
chemin d’évaluation borné existant reste disponible hors du domaine prouvé.
Les limites de travail et de pile ne sont pas augmentées.

`ThunkFusion` relance cette simplification uniquement lorsqu’un worker strict
est effectivement consommé. Le calcul interne fermé devient alors un
incrément constant, ce qui permet à l’optimisation affine existante de réduire
la boucle externe en arithmétique sur le compteur runtime. Aucun nom de
benchmark ni résultat attendu n’intervient dans ces règles.

## Validation

- **61 tests ciblés** passent, dont 252 combinaisons de compteur, accumulateur
  et incrément vérifiées contre un oracle entier exact.
- La fixture étendue produit les mêmes résultats que son oracle JavaScript
  avec les hôtes JS et natif, en Release et Dev. Elle couvre les grands comptes,
  les débordements, les accumulateurs négatifs, zéro et une entrée runtime.
- **84 variantes d’entrée** concordent avant/après et avec le C inchangé.
  Les sondes temporaires substituent seulement le retour de la frontière
  opaque et vérifient exactement un passage par cette frontière par action.
- L’assemblage de production conserve l’appel à `opaqueValue` via le worker
  FFI et utilise son retour dans le calcul de Lazy.
- La comparaison des **610 sections Go App14** et **657 sections AppAll37**
  ne trouve de changement que dans `p_root/Test_LazyEvaluation.go`.
  Les autres sections, les imports et le runtime sont identiques.
- Les **306 résultats** des douze processus et leurs lots calibrés sont
  validés. Les empreintes des benchmarks, du harnais, des références et des
  exécutables sont contrôlées avant et après les mesures.

Les trois processus App14 donnent **738,912–747,584 ns avant** et
**12,860–12,952 ns après** pour Lazy. AppAll37 confirme le gain :
**733,470 → 13,197 ns**, soit **55,58×**. Ces plages sont les valeurs observées,
pas des intervalles de confiance. Aucun cas n’augmente de plus de 5 % dans
les deux campagnes. Les tentatives intermédiaires sont identifiées dans
l’archive et ne participent pas aux mesures finales.

## Protocole et reproduction

Apple M4 Pro, 48 Gio, Go 1.27.0, darwin/arm64, Release, GOGC=800, sans PGO,
GOMAXPROCS par défaut. Chaque paire utilise trois processus par variante,
en ordre AB/BA/AB. Le harnais conserve ses échauffements, sa calibration et
le minimum de dix batches ; la valeur publiée est la médiane des trois minima
de processus. Tous les builds et tests étaient terminés avant la campagne.
La machine n’était pas isolée des autres activités utilisateur.

L’entrée App à 14 cas fournit les chiffres Stable. La paire AppAll à 37 cas
contrôle les régressions et fournit les 23 chiffres Incl WIP. Le README
actualise uniquement la colonne Go Release dans ses tableaux existants.
Les autres colonnes et les références gardent leurs mesures.

Le script de collecte est inclus dans l’archive. Son rejeu intégral vérifie
aussi le catalogue antérieur à cette publication. Pour réexécuter directement
les deux paires de binaires figés dans de nouveaux répertoires :

```sh
env -u GOMAXPROCS -u PPROF GOGC=800 python3 -B bin/benchmark/measure.py \
  --plan var/benchmark/go-lazy-20261125/campaign/core-plan.json \
  --output var/benchmark/go-lazy-20261125/replay-core

env -u GOMAXPROCS -u PPROF GOGC=800 python3 -B bin/benchmark/js-ratios.py \
  --before var/benchmark/go-church-state-20261125/after-all \
  --after var/benchmark/go-lazy-20261125/after-all \
  --output var/benchmark/go-lazy-20261125/replay-all
```

Les quatre indicateurs se recalculent avec les temps C conservés dans
`campaign.frozen_reference.c_times_us` de l’archive.
